# 历史索引与归档 RFC

最后更新：2026-05-07

当前状态：SQLite 历史索引和历史归档迁移已经作为本地旁路能力接入维护区。主快照仍是权威状态；历史库是可重建索引/归档，不需要 Docker 或外部数据库，不作为当前单人本地正式使用阻塞项。

## 决策

OPC 当前不把主状态整体迁移到数据库。主快照仍是权威状态；本地数据库只作为可重建的旁路历史索引和旧历史归档表。

理由：

- 主快照便于本地备份、安全检查点和人工排查。
- 现有产品状态结构仍在快速演进，直接迁移主存储会放大 schema 风险。
- 当前痛点是检索和索引，不是事务型写入。
- 本地历史索引损坏时可以从主快照重建，不影响主状态。

## 当前实现

维护巡检或显式重建入口会生成：

```text
~/Library/Application Support/OPCCompany/company-history.sqlite3
```

索引表覆盖：

- 聊天消息。
- 公司事件。
- 任务。
- 员工工作项。
- 审批。
- 产物。
- 验收。
- 产品记忆。
- 通信日志。
- 验收门禁。
- 员工协作消息。

普通主状态保存不做同步全量重建，避免高频状态保存被历史索引拖慢。终端大厅维护区提供「历史索引巡检」，用于重建索引、写入验收记录并向技术负责人汇报。

## 当前归档迁移

维护区已提供「历史归档迁移」入口。当前迁移只把超过保留期的旧记录复制到本地归档表：

- 聊天消息。
- 公司事件。
- 通信日志。
- 员工协作消息。

当前迁移不裁剪主快照、不删除本地文件、不启动模型任务。归档表损坏时仍可从主快照重建；归档失败不能影响主状态保存。

## 后续裁剪触发条件

只有满足任意条件时，才考虑把已归档旧历史从主快照裁剪：

- `company-state.json` 超过 50 MB。
- App 启动加载快照超过 1 秒。
- 用户需要跨月/跨产品全文搜索并且当前索引查询无法满足。
- 安全检查点体积过大，影响回滚或备份体验。

## 归档原则

- 主快照保留最近活跃状态和最近记录。
- 本地归档表保存旧消息、旧事件、旧通信日志和旧协作消息。
- 归档必须可导出、可重建、可按产品删除。
- 归档失败不能影响主状态保存。
