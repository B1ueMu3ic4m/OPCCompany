# OPC 多 Agent 架构升级方案

最后更新：2026-05-07

当前状态：多 Agent 架构升级已达到单人本地正式使用基线。本文保留方案和架构说明；当前验收状态、最新测试数和 bundle 版本以 `OPC_COMPANY.md` 与 `docs/RUNBOOK.md` 为准。

## 本轮目标

把 OPC 从“有多个员工和任务列表”升级为“有可追踪多 Agent 协作链路”。

完成状态：本轮多 Agent 架构升级的底层协作模型已经落地，并由 `runMultiAgentArchitectureClosureDrill`、架构体检和测试覆盖。默认产品如果还没有运行闭环演练，终端大厅会显示未闭合或待加强；这表示当前产品缺少演练证据，不表示代码能力缺失。

2026-05-07 正式使用基线补充：

- 员工 prompt、工单 prompt、返工 prompt、协作消息和 CLI 续会话已加 token 预算边界。
- 默认可见老板界面不显示维护类风险、后台路径或底层命令参数。
- 终端大厅「运行全部」在默认汇报提示词且会触发多名员工时会先弹中文确认，避免误消耗整支团队命令行额度。
- 继续增强时只处理真实阻塞项或用户明确提出的新目标，不再为了维持循环而扩大问题。

本轮先把底层协作模型做稳；2026-05-01 起，通信网关和历史索引已进入可验证增强阶段：

- CTO 能把老板目标变成结构化任务图。

- 老板只看到结果、风险、待审批和交付摘要。
- 所有过程能被测试验证，不能只靠 UI 假展示。

- 本地历史索引已作为旁路索引接入，主快照仍是权威状态；终端大厅维护区可以重建和巡检历史索引，也可以把旧记录复制到本地归档表。

## 架构原则

### 1. 公司层级

```text
老板
  -> CTO Supervisor
      -> 员工 Agent
      -> 审查 Agent
      -> 产物/验收
      -> 老板汇报/审批
```

老板不直接管理复杂分支；CTO 是默认调度者。

### 2. 消息总线

新增 `AgentMessageEnvelope`，所有 Agent 协作都通过消息记录：

- CTO 派任务给员工。
- 员工向 CTO 回传结果。
- CTO 请求审查员验收。
- 审查员给 CTO 反馈。
- CTO 给老板提交汇报或审批请求。

消息不是普通聊天，它是后台协作记录。普通聊天只显示给老板看的自然语言。

### 3. 任务图

现有 `CompanyTask` 继续作为任务节点。本轮新增轻量任务图视角：

- 目标拆解任务。
- 并行员工任务。
- 审查任务。
- 老板审批任务。

当前已在闭环追踪层补上派生 `MultiAgentTaskGraphNode` / `MultiAgentTaskGraphEdge`：继续复用 `CompanyTask` 作为真实任务节点，但从消息、审批和验收记录生成显式边证据，展示 CTO 派发、员工回传、审查结论、老板决策回流。架构体检的显式任务图项也会检查派生节点和边。后续如果需要更复杂依赖，再把派生图升级为持久化任务图。

架构体检里的交付证据库和验收门禁必须挂到同一条闭环追踪上：只有 `MultiAgentClosureTrace.artifactIDs` / `verificationIDs` / `reviewGateIDs` 能让对应模块闭合。产品里散落的报告、验收或门禁记录只能算“待加强”，不能替代一次从技术负责人拆解到老板验收的完整证据链。

### 4. CTO Supervisor Loop

新增确定性调度入口：

- `startCTOSupervisorGoal(goal:)`
- `advanceCTOSupervisorLoop()`

第一阶段用确定性逻辑，后续再把规划部分交给真实模型：

1. 创建 CTO 拆解任务。
2. 给 UI/工程/审查等员工创建任务。
3. 写入工作队列。
4. 通过消息总线派发。
5. 员工完成后通知 CTO。
6. CTO 触发审查和老板汇报。

### 5. UI 分层

老板总控台只显示：

- 是否有待老板审批。
- 产品进度。
- 最近交付。
- 员工进度摘要。

流程图/员工工作台可以显示：

- Agent 消息链路。
- CTO 调度状态。
- 员工队列。
- 审查回传。

## 跨员工显式交接（员工 → 员工）

- `AgentMessageKind.employeeHandoff` 是员工之间的结构化交接证据，区别于技术负责人居中派发、回传、审查和审批。
- `CompanyStore.postEmployeeHandoff(productID:fromAgentID:toAgentID:taskID:subject:body:)`：
  - 仅允许同一产品团队内部、非老板的两个不同员工之间产生记录；
  - 跨产品、跨产品任务、老板参与、自交接或缺失员工时返回 nil 并写入风险事件；
  - 写入 `agentMessages`（状态为待确认），不写老板首页聊天消息、不创建 `.opc/jobs/`、不触发模型任务，符合 § 5.3「跨员工交接必须留下消息和产物记录」的合规要求；
  - 默认 productID 为 `selectedProductID`，可显式传入以保证当前产品隔离不被错位调用绕过。
- 闭环演练 `runMultiAgentArchitectureClosureDrill` 在工程完成和审查启动之间补一条「工程师 → 审查员」交接，使闭环追踪的消息证据链包含任务派发、员工交接、审查请求、员工回传、审批请求和审批结果等关键消息。
- 员工工作台「我的协作收件箱」、产品详情「员工协作链路」、流程图「消息流 / 协作链路」、「员工协作消息中心」复用 `AgentMessageRow`，全部自动显示中文标题「员工交接」和蓝色交接图标；老板总控台不展示。

## 员工收件箱单条消息确认（员工 → 员工）

- `CompanyStore.acknowledgeSelectedAgentMessage(_ messageID:)`：单条确认必须满足「当前产品 + `toAgentID == selectedAgentID` + 待确认」三条；不满足任意一条返回 false 且不修改状态，不影响出站消息、其他员工消息或跨产品消息。
- 确认成功后写入 `acknowledgedAt`，并在事件流追加中文「员工协作收件箱已确认一条」事件。不写老板首页消息，不触发模型任务，不创建作业档案。
- `AgentMessageRow` 接受可选 `onAcknowledge` 闭包：员工工作台「我的协作收件箱」、员工消息中心 (`AgentMessageCenterSheet(scope: .agent)`) 在入站待确认消息上显示中文按钮「确认这条」；产品级面板（产品详情「员工协作链路」、流程图「消息流 / 协作链路」、`AgentMessageCenterSheet(scope: .product)`）保持只读，不替别人确认。
- 批量「标记我的消息已读」按钮保留：单条确认是逐条闭环路径，批量按钮是清理路径，二者并列；员工交接巡检 `runEmployeeHandoffAuditForSelectedProduct` 在两条路径下都能把待确认数减少到通过。

## 员工工作台快捷发起员工交接（员工 → 员工）

- `CompanyStore.selectedAgentHandoffRecipients` / `selectedAgentHandoffTaskCandidates` / `postSelectedAgentHandoff(toAgentID:taskID:subject:body:)`：以当前选中员工为发送方，过滤同产品团队、非老板、非自己作为可交接接收人，并把当前产品里 ownerID 等于该员工的任务作为可关联任务（按状态优先级排序）。
- 内部仍调用 `postEmployeeHandoff`，保留同产品守门、老板/跨团队保护；主题或正文为空时由消息总线兜底中文文案。
- `AgentDeskWorkspace` 新增「发起员工交接」中文面板，紧贴「我的协作收件箱」：下拉菜单选对方、下拉菜单选任务（包含「无关联任务」选项）、输入框写主题和正文、按钮发送；发送成功提示「已写入员工协作消息总线，待对方在收件箱确认」并清空输入。
- 老板/未加入团队/无可接收人时分别显示中文空状态并禁用发送；不进入老板总控台；不触发模型任务、不创建作业档案、不写老板首页消息。Store 层会拒绝把非本人负责的任务挂到快捷交接上，避免界面旧选择或外部调用串任务。
- 手动交接和闭环演练写入的交接复用同一条总线，由「员工交接待确认巡检」统一统计。

## 员工交接待确认巡检（技术负责人后台）

- `CompanyStore.employeeHandoffAuditText(staleAfter:)` / `runEmployeeHandoffAuditForSelectedProduct(staleAfter:)`：纯只读巡检，按当前产品维度统计员工交接消息（`AgentMessageKind.employeeHandoff`）的总数、待确认、已确认、超时待确认。默认阈值 180 秒，最低 60 秒。
- 报告写入 `VerificationRecord("员工交接待确认巡检")`、技术负责人系统消息和事件流；存在超时待确认时状态为失败并追加「员工交接超时待确认」风险事件，仅有待确认时状态为警告，无任何待确认时状态为通过。
- 巡检不会修改交接 status、不会创建 `.opc/jobs/`、不会触发模型任务；要清除待确认仍由对应员工在「我的协作收件箱」点击「标记我的消息已读」。
- 界面入口位于 `LocalMaintenanceCenter`（技术负责人和运维后台），中文按钮「运行员工交接巡检」加始终可见的「员工交接巡检预览」卡片，老板总控台不展示。
- 跨产品隔离：仅遍历当前产品下的员工协作消息，切换产品后 B 产品看不到 A 产品的交接。

## 命令行作业幽灵巡检（技术负责人后台）

- `CompanyStore.jobArchiveStaleAuditText(staleAfter:)` / `runJobArchiveStaleAuditForSelectedProduct(staleAfter:)`：扫描当前产品根目录的命令行作业档案，识别仍标记运行中、更新时间超过阈值、但没有真实员工运行占用的旧作业档案。
- 实际巡检会把这些幽灵作业写回为已中断，保留原状态、中断时间和中文中断原因；真实运行占用和未超时作业只进入报告，不会被打断。
- 报告只写 `VerificationRecord("命令行作业幽灵巡检")` 和事件流，不写老板聊天、不写员工协作消息、不创建新的作业档案、不触发模型任务。
- 界面入口位于 `LocalMaintenanceCenter`，中文按钮「运行命令行作业幽灵巡检」加「命令行作业幽灵巡检预览」卡片；老板总控台不展示后台维护复杂度。
- 与运行会话健康巡检配套：员工运行会话绑定产品归属，用于识别产品漂移；切换产品后不会把同一员工的其他产品会话当作当前产品运行占用。

## 运维预检可见文案中文化

- 终端大厅里的运行前预检、命令行链路压测预检和发车计划只展示中文「运行摘要」「运行清单」「任务注入」等产品话术，不直接展示底层命令参数、提示词占位符或调试开关。
- 运行会话健康巡检只展示「异常占用」「最近错误」「后端配置匹配/不匹配」等中文摘要，不展示底层签名、内部状态枚举或错误字段名。
- 命令行与工作区隔离体检只展示员工工作区、会话日志、运行会话和独立执行区的中文摘要，不展示内部文件名、元数据路径或独立执行区底层目录。
- 真实终端工作区预览只展示终端工具是否就绪、已连接席位数量和每个员工的执行位置摘要，不展示底层会话名、窗口名或终端工具路径。
- 本地维护区的隔离体检和真实终端工作区采用默认摘要加折叠详情：默认视图服务 CTO/老板侧判断，折叠详情只给运维排障，不作为普通可见文案。
- 员工工作台的会话状态摘要把英文退出标记转换成中文退出码摘要；员工档案只展示命令行工具名，不展示完整底层参数。
- 命令行任务和聊天链路的终端日志只显示中文运行摘要，不显示完整命令数组、命令参数或内部会话日志文件名；异常占用恢复和安全检查点也只显示中文状态与本机存档摘要。
- 员工执行提示词只告诉模型“员工工作区由 OPC 在本机维护”，不把 `Library/Application Support` 下的绝对路径交给模型，避免模型复述内部路径进入用户可见回复。
- 保留 Codex、Claude Code、Gemini、OpenAI、模型名和必要路径等用户配置名；隐藏的是系统生成的内部参数，不影响真实执行。

## 审查员个人审查队列（员工工作台）

- `CompanyStore.selectedAgentReviewQueue` 只返回当前产品、当前选中员工本人负责、状态为「待审查」的任务；员工必须是审查员或具备 review 技能，且必须已加入当前产品团队。
- `CompanyStore.completeReviewByOwner(taskID:summary:)` 是审查员签字通过路径：任务进入「完成」，写入「审查完成」协作消息，更新验收门禁为「验证通过」，追加中文事件；不写老板首页消息，不启动模型任务。
- `CompanyStore.rejectReviewByOwner(taskID:reason:)` 是审查员打回路径：任务回到「已分配」，写入「审查完成」协作消息，更新验收门禁为「验证警告」，追加中文风险事件；不写老板首页消息，不启动模型任务。
- `AgentMessageEnvelope.reviewOutcome` 用结构化字段记录审查结果：通过为 `.passed`，打回为 `.rejected`。历史消息没有该字段时保持 nil，不影响旧快照加载；巡检和闭环追踪不需要解析消息主题来判断结果。
- 如果被打回的是「审查验收：目标」这类技术负责人闭环任务，Store 会找到同目标「员工执行：目标」任务，把它重新置为「已分配」并放回执行员工队列；重派发消息正文包含打回原因，但不会启动模型任务、不会创建命令行作业档案、不会写老板首页消息。
- `CompanyStore.selectedAgentReworkQueue` 给当前员工筛出自己的返工队列项；员工工作台「员工工作队列」会显示返工计数，队列卡片用「返工」标签和「原因：…」突出审查打回原因，工程师无需到技术负责人后台翻消息。
- `CompanyStore.selectedProductReworkSummaryText()` 给技术负责人后台输出当前产品返工追踪摘要：返工队列项数量、任务、状态、执行员工和打回原因。该摘要放在「多员工架构体检」区域，不进入老板总控台。
- 工程师完成返工工作项后，`completeWorkItem` 会识别「打回原因」并重新打开同目标「审查验收：目标」任务：审查任务进入「待审查」，写入「返工后复审」消息和待审查门禁，并从工程师返工队列中移除已完成返工项；审查员个人待审面板会用中文标签标明「返工后复审」。
- 审查员对技术负责人闭环里的「审查验收：目标」签字通过后，`completeReviewByOwner` 会自动把同目标「老板审批：目标」提交到老板决策中心：写入技术负责人推进消息、创建老板审批请求，并避免重复创建同一老板审批。
- 老板批准技术负责人闭环里的「老板审批：目标」后，`decideApproval` 会把同目标的技术负责人拆解、员工执行、审查验收和老板审批任务组收束为完成，并写入验收报告、老板验收通过记录和验收完成消息；普通风险审批仍保持「批准后继续运行」语义，不被这条最终交付规则影响。
- 老板驳回技术负责人闭环里的「老板审批：目标」后，`decideApproval` 只对同目标闭环触发返工回流：老板审批任务退出风险列表并等待返工后再次提交，员工执行任务重新进入执行员工返工队列，审查验收任务退回待后续复审；返工完成后会重新进入审查员个人待审队列，复审通过可再次提交新的老板审批。普通风险审批仍保持「驳回后阻塞」语义。
- 最终审批的批准/驳回回流使用审批记录自己的 productID 写入任务、队列、消息和事件；即使老板在另一个产品页签处理旧审批，也不会把返工队列写到当前选中的产品。公开的手动入队入口仍只允许当前产品任务进入当前产品队列。
- 员工工作台在审查员视角显示「我的待审任务」面板，提供「完成审查」和「打回返工」两个真实动作，审查意见会进入协作消息和验收门禁。
- 该入口属于员工执行视图，不进入老板总控台；老板仍只看技术负责人汇总后的结果、风险、审批和交付。

## 闭环演练复盘摘要（技术负责人后台）

- `CompanyStore.selectedProductClosureDrillSummaryText()` 给当前产品输出最近一次多员工闭环演练的复盘摘要：目标、状态、完成度、任务、消息、审批、审查门禁、产物、验收计数、下一步建议。
- 摘要展示在技术负责人后台「多员工架构体检」面板（`ClosureDrillSummaryCard`），不进入老板总控台。
- 无闭环时给出统一中文空状态：「还没有运行多员工闭环演练。请先在技术负责人后台点击『运行闭环演练』…」。
- 不暴露后端、命令行、模型等运维细节；明细仍由「查看闭环详情」与「打开决策中心」承担。
